Section 00

The 60-second version

If you read nothing else, read this. There are two separate slowness problems with two different root causes.

Problem 1 — Getting into the app

Scenario cards and session cards are slow because the API sends the entire contents of every scenario and session, including giant blobs the cards never display.

The dashboard — your landing page — downloads 27 MB to display four integers. The scenario library downloads 13 MB to draw cards that need 129 KB.

Problem 2 — Inside a simulation

Opening the social feed runs a database query that reads 30,706 rows in order to show 1,000, because one filter accidentally disables the index built for exactly this query.

On a cold cache that takes 6.8 seconds. And sending a message shows the player nothing at all until three network round trips finish.

Two things that will mislead you

1. Shrinking the page size does not fix the slowness. I measured it: dropping the limit from 1000 to 50 leaves the work the database does completely unchanged (7,456 buffers either way). It fixes the download size, not the wait.

2. But adding an index isn't the answer either. The right index already exists — forcing Postgres to use it gives 81.7 ms. The actual bug is that the planner mis-estimates the row count by 94× and picks the wrong plan. The fix is to delete a predicate that does nothing, not to add anything.

Both details are in the trap, and the knock-on risks of every proposed fix are in drawbacks.

And you don't need a bigger Supabase plan yet. 99.94% of reads already come from memory. The waste is a few queries that read finished exercises' data to answer questions about the current one, fixable with three index migrations. See Part 3.
Section 01

First, ruling out the usual suspect

Before blaming anything, I profiled the queries behind every slow screen. The database is not the problem on the card pages — it is roughly a thousand times faster than the thing it feeds.

Query behind the screenExecution timeVerdict
Trainer session list (20 rows, sorted)0.399 msFine
Full scenario list (99 rows, sorted)0.390 msFine

Conclusion: the time is not spent finding the data. It is spent serialising, transferring, and parsing data nobody asked to see — and, inside simulations, on one query whose index has been accidentally disabled. Those are the two things this document is about.

A consequence worth stating up front: adding indexes to sessions or session_participants would be wasted work. Those tables hold 265 rows and a handful respectively. The planner scans them in a fraction of a millisecond. Indexes there would cost write performance and buy nothing. There is one genuinely missing index, and one accidentally-useless one — both covered below.

BUG-04 The participants join is paid for and then thrown away — and three stats are silently broken Medium · latent bug

server/routes/sessions.ts:85 vs pages/Sessions.tsx:29

The query selects session_participants(...), so the JSON key is session_participants. But the frontend reads s.participants. Nothing aliases it on the list endpoint — though the single-session endpoint at line 1217 does alias it correctly.

So s.participants is permanently undefined, which means:

  • The participant count chip on each session card never renders
  • The "participants" tile on the Sessions page is always 0
  • The dashboard participants stat is always null

...while the app faithfully transfers the full participants join plus a nested user_profiles(*) for every participant.

Fix

Alias it to participants:session_participants(user_id) in the slim select. One change fixes the bug and drops the weight simultaneously.

BUG-05 No compression anywhere High

server/index.ts — no compression middleware

I searched the entire server and the Vercel config. Every JSON response above crosses the wire raw. JSON of this shape compresses roughly 10×.

This is one line of code for an order-of-magnitude improvement on every single endpoint, and it multiplies every other fix in this document.

BUG-09 The scenario library makes 99 separate count requests, in 9 sequential waves Medium

server/routes/scenarios.ts:168–198

injectCountsFor issues one PostgREST HEAD count per scenario, batched 12 at a time. 99 scenarios means 9 sequential waves of network calls, recurring every time the 60-second cache expires. Each individual query is fast (0.235 ms) — the cost is entirely round trips.

The code comment correctly explains why it was written this way: a grouped IN query would hit PostgREST's 1000-row cap. That reasoning is sound; the answer is a database function, which sidesteps the cap entirely.

BUG-10 One genuinely missing index — and the existing one is backwards Medium

Table scenario_injects — 33,071 rows / 23 MB

The single grouped query that would replace BUG-09's 99 calls is currently slow:

BUG-11 Nothing is cached, so every navigation refetches everything Medium

No react-query / SWR / sessionStorage layer anywhere

Dashboard → Scenarios → Sessions → Scenarios refetches all of it from scratch. The shimmer skeleton appears on every single visit even when nothing has changed. This is the difference between "fast" and the "almost instantaneous" you asked for — instant on a repeat visit is only achievable with a cache.

Security note for whoever builds this: cache keys must include the user id and must be cleared on sign-out, or one user's cards can flash on screen for the next user on a shared machine.

Two details make this worse than it first appears:

Section 04

Part 3 — Old exercises' data being read, and why you don't need a bigger plan

Added 24 Sep 2026. The question was whether the database needs a bigger Supabase compute size. It doesn't, yet. The waste comes from a few specific queries that read finished exercises' data to answer questions about the current one.

The capacity answer

Your database serves 99.94% of all reads from fast memory: 1.73 billion hits against 984,370 disk reads. Supabase considers anything above 99% healthy. That is on a server with roughly 1 GB of memory (inferred from its settings) holding a 1.76 GB database. No compute upgrade is needed now. Upgrade only if that rate falls below 99%.

BUG-25 The statement watchdog reads every finished exercise to find the current one High · grows every exercise

server/services/statementWatchdogService.ts:306–312

During every exercise, the watchdog keeps asking for "this exercise's oldest 100 official and player posts":

.from('social_posts')
.eq('session_id', sessionId)
.in('author_type', ['official_account', 'player'])
.order('created_at', { ascending: true })
.limit(100);

There is no index on exercise + time, so on a large exercise Postgres walks the whole table's time index from the very first post ever written:

all posts, in time order ──────────────────────────────────────────►
[ exercise 1 ][ exercise 2 ][ ... ][ exercise 96 ][ the current exercise ]

ExercisePlanPosts discardedPagesTime

Busiest (54,865 posts)table-wide time index104,36485,545576 ms

Across its 2,800 recorded runs, it averaged 26,348 pages each. It gets slower with every exercise you run, because the history in front of the current one keeps growing.

Fix

An index on social_posts (session_id, created_at), replacing the plain session index so the index count doesn't grow. The database then jumps straight to this exercise's posts in time order and stops at 100.

The trap: "only read posts since this exercise started". It looks like a one-line fix and measures well: 10.7 ms and 1,261 pages. But 2,681 posts across 82 exercises are dated before their own exercise was created. 2,458 of them are official-account posts, deliberately backdated up to 30 days (ambientContentService.ts 402–425) to give each organisation's page a pre-crisis history, and the watchdog reads official posts. That condition would silently hide them. This is why the fix is an index, not a date condition.

BUG-26 The events table sweeps every exercise's events of a type High · top disk reader

Table session_events — indexes on (session_id) and (event_type) only

session_events is the table read most from disk (389,754 pages). Its heaviest queries filter by exercise and event type (32,610 runs at 767 pages each; 16,125 more at 2,915 pages each), but there are only separate indexes for each. So the database intersects this exercise's events with every exercise's events of that type: 70,767 entries of one type, to find one exercise's.

Fix

One combined index on (session_id, event_type, created_at), replacing the plain session index. The index count stays the same.

BUG-27 Deleting a post scans the whole posts table Medium · blocks archiving

Foreign key social_posts_original_post_id_fkey — no index

original_post_id links a repost to its original, and nothing indexes it. So every time a post is deleted, the database scans the whole table to check that no repost points at it. The 28 recorded deletions averaged 902 ms and 169,157 pages each, which is very likely also where the table's 1,416 full scans come from. All the other links (replies, likes, flags, engagement log) are already indexed.

Fix

A tiny partial index on original_post_id (only 10 posts are reposts). This is required before any archive job, which deletes posts in bulk.

So, no bigger plan for now. Three index migrations stop live exercises from reading finished exercises' data. Archiving finished exercises (the plan's §7a.5) is the long-term tidy-up, but it carries real risks, covered in the drawbacks section as RISK-08 to RISK-12.
Section 05

The trap: why the obvious fix doesn't work

This is the most important page in the document. Get this wrong and you will ship a fix, see no improvement, and conclude the diagnosis was wrong.

Measured, not theorised

Everyone's first instinct on BUG-13 is: "it asks for 1,000 posts, so ask for 50." I measured exactly that. Here is what happens to the work the database does:

QueryBuffers touchedRows readTime (warm)
limit=1000 + country filter7,45630,70688 ms
limit=50 + country filter7,45630,70678 ms

Identical. The LIMIT changes nothing about the work performed, because a Sort cannot emit its first row until it has seen every input row. The bitmap scan must materialise all 30,706 matches regardless of how many you eventually want. The LIMIT only trims what gets serialised and sent.

Smaller page size fixes…

  • ~1.4 MB download → ~70 KB
  • 1,000 React nodes → 50
  • The 37 KB URL in BUG-20

Does not fix: the 6.8-second wait.

Getting the right plan fixes…

  • 7,456 buffers → ~2,670
  • The Sort node disappears entirely
  • The 6.8-second cold open

Does not fix: the 1.4 MB payload.

Do both — they address different problems and neither substitutes for the other. If you can only do one, fix the query plan first: the multi-second stall is what makes the product feel broken, and it is the cheaper of the two.

The second surprise: no new index is needed at all

The first draft of the fix plan proposed adding a composite index. Further measurement showed that was wrong. I forced Postgres to do an ordered walk on the index that already exists, leaving the country filter in place to be applied inline:

enable_bitmapscan = off; enable_sort = off; — same feed query
Limit (actual time=13.742..81.526 rows=1000)
  Buffers: hit=2669 read=109
  -> Index Scan using idx_social_posts_virality   ← already exists!
       Index Cond: (session_id = '...')
       Filter: (NOT platform_removed) AND (country IS NULL OR country = 'Singapore')
       Rows Removed by Filter: 1741    ← not 24,159
  (no Sort node — the index supplies the order, so it stops at 1000)
Execution Time: 81.725 ms

81.7 ms, using an index you already have. So what is actually broken is not the index — it is the planner's row estimate. It predicts 325 rows where reality is 30,706, and with a cost model that wrong it reaches for the bitmap.

I confirmed the planner will not find the good plan on its own: disabling only the bitmap scan made it choose idx_social_posts_platform and filter 94,132 rows — 5,557 ms, worse than today.

So the real fix is deletion, not addition. Removing the country predicate when the session has no country-scoped content (true for 99 of 103 sessions) lets the planner pick the good plan unaided — measured at 168 ms. No migration, no new index, no write-amplification cost. That is the primary fix.
Still open: the 4 sessions that genuinely use country scoping keep the bad plan, because they actually need the predicate. Options there are extended statistics to repair the row estimate, restructuring the predicate to preserve an equality, or accepting it given how small those sessions are. Resolve before calling the feed fixed.

Index hygiene, found along the way

While measuring, the usage statistics turned up real waste. social_posts carries 16 indexes — 78 MB of index against 134 MB of heap (58%).

IndexScans everSizeVerdict
idx_social_posts_target_player_ids0872 kBDead — but see below
idx_social_posts_surfaced016 kBDead — but see below
idx_social_posts_shared_article016 kBDroppable
idx_social_posts_algorithm_sort14,40425 MBRedundant — drop
idx_social_posts_virality16,84217 MBKeep — this is the one that works

idx_social_posts_virality is a strict prefix of idx_social_posts_algorithm_sort, and only one query in the codebase orders by virality_score — without using created_at as a tiebreaker. So the longer index's third column earns nothing.

Why that matters beyond disk space: the engagement engine rewrites virality_score for every recent post every 30 seconds, and each of those updates must maintain both virality indexes. Dropping one halves that write cost.

Do not drop the two zero-scan targeting indexes yet. They exist for exactly the visibility filter that currently runs in JavaScript instead of SQL (see the next section). They are unused because of that bug. Fix it first, then re-check their scan counts — they should start earning their keep.
Section 06

Drawbacks — what these fixes break

A deliberate review of the second-order effects. Four of these were serious enough to change the plan; two are failure modes the fixes would newly introduce.

RISK-01 Shrinking the page size would break post visibility Blocker

server/routes/socialMedia.ts:158 (limit) vs 204–221 (filter)

The endpoint applies the LIMIT in SQL, then filters the returned rows in JavaScript on is_surfaced_to_session, target_player_ids and target_demographics. Filtering after paginating is a classic bug, currently masked by the huge page size.

Measure (busiest session)Value
Candidate posts30,706
is_surfaced_to_session0
Has target_player_ids1,160
Has target_demographics368
Filtered out for a typical player1,528 (~5%)
  • At limit=1000, ~50 rows vanish silently. Nobody notices.
  • At limit=50, each page loses 2–3 rows, so pages come back different sizes and scroll stutters.
  • count is the pre-filter count, so any "are there more pages" logic is wrong by construction.
  • A player whose page is mostly targeted content could get a near-empty page while plenty of visible content exists below.
Resolution — measured, and better than expected

The rule looked hard to express in SQL because the JavaScript handles arbitrary keys and arrays. The real data is far simpler: target_player_ids is a native uuid[] (not JSONB), and target_demographics only ever contains one key, race, always a string — 3,653 strings, zero arrays.

the whole visibility rule, in plain SQL
is_surfaced_to_session
or (target_player_ids is not null and :uid = any(target_player_ids))
or (target_player_ids is null and target_demographics is null)
or (target_player_ids is null and target_demographics is not null
    and lower(target_demographics->>'race') = lower(:player_race))

Measured with this filter in SQL and the country predicate dropped: 30.1 ms at 1,203 buffers, returning 50 posts that are all genuinely visible. With the case fix below, 4.8 ms.

RISK-02 Sorting by a constantly-rewritten column makes pagination unstable Blocker

server/services/engagementAlgorithmService.ts:330–360

virality_score is rewritten every 30 seconds for every top-level post from the last 45 minutes. Offset pagination over a volatile sort key means a post can move between page 1 and page 2 while the player scrolls — producing duplicates or skipped items.

The existing frozenOrder mechanism freezes the feed against new arrivals. It does not protect against reordering of rows already fetched.

Resolution

Keyset pagination on (virality_score, id), which is trivial inside a database function and awkward outside one:

and (:after_score is null or (p.virality_score, p.id) < (:after_score, :after_id))
order by p.virality_score desc, p.id desc

One check at implementation time: adding id as a tiebreaker makes the sort (virality_score DESC, id DESC) while the index is (session_id, virality_score DESC). Verify the planner still does an ordered walk rather than re-sorting. If it doesn't, the tiebreaker moves into the index — the one scenario where a migration comes back into scope.

RISK-02b Fixing the demographic case bug changes what players see Deliberate change

Moving the filter into SQL surfaces a latent bug: the JavaScript compares with ===, so a player whose race is recorded as Chinese never matches the 1,267 posts targeting chinese. Per review decision this is fixed in the same change rather than deferred — so slightly more content becomes visible, which must not look like a regression.

I quantified the blast radius before recommending it:

MeasureValue
Distinct target races20 (18 lowercased)
Players affected4 of 155
Total post-views newly visible15
Worst single playergains 10 posts
Performance cost of lower()none — 4.8 ms, same plan
Resolution

Safe to fix in the same change — the effect is 15 post-views across 4 players. Every target race already matches some player, so nothing is orphaned wholesale. Call it out in the release note so the extra visible content reads as a fix rather than a bug.

RISK-03 Code splitting adds a whole-app crash that cannot happen today High

frontend/src/components/ErrorBoundary.tsx — one global boundary

ErrorBoundary is a single top-level boundary. When it fires it replaces the entire application with a full-screen "Something went wrong" and a manual Reload button. There are no per-route boundaries.

With one bundle a chunk cannot fail after load — all code is already in memory. Splitting changes that twice over:

  • Flaky network on a lazy route → the dynamic import rejects → the player loses the whole screen mid-exercise.
  • Deploying while someone has the app open → their entry chunk references the old hashed filenames. If those assets are gone, navigating anywhere new 404s into the same full-screen error. For a trainer running a live session, severe.
Resolution — Vite has a built-in hook for exactly this
main.tsx — register before createRoot
window.addEventListener('vite:preloadError', (event) => {
  event.preventDefault();      // stop it reaching the global ErrorBoundary
  window.location.reload();    // fetch the current index + chunk manifest
});

Vite fires this event when a dynamic import fails — precisely the stale-chunk-after-deploy case. It turns "trainer loses the whole screen mid-exercise" into "the page reloads". Guard against a reload loop with a sessionStorage flag so it self-reloads at most once. Pair it with per-route error boundaries so a genuinely broken route doesn't take down the app shell.

RISK-04 Removing the polls creates permanent staleness Medium

frontend/src/lib/websocketClient.ts — reconnectionAttempts: 5

After five failed reconnects the socket client stops trying, permanently. Today the 15-second poll hides that: a player whose socket dropped still gets fresh badges.

Remove the poll and rely on the WebSocket alone, and a single network blip leaves that player permanently stale with no recovery short of a manual reload — during a live exercise.

Resolution — do both, they're cheap 
// websocketClient.ts
reconnection: true,
reconnectionAttempts: Infinity,   // was 5 — this was the cliff
reconnectionDelay: 1000,
reconnectionDelayMax: 30000,      // back off instead of hammering
randomizationFactor: 0.5,

Then keep a slow poll at 60–120 s rather than deleting it — still a 4–8× reduction, and it also covers the case where the socket is "connected" but the server has stopped broadcasting. Surface isConnected in the device chrome so a stuck player can see why nothing is arriving.

RISK-05 Optimistic send re-opens a race that TeamChat fights with 160 lines Medium

Adding a local temp row while a WebSocket broadcast of the same message is in flight is exactly the race ChatInterface handles by matching content strings across three refs plus a timeout fallback (lines 378–539). Repeating that in three more places triples the surface area for duplicate and ghost messages.

Resolution — verified viable against the schema

I checked all four message tables. Every one has a uuid primary key with a uuid_generate_v4() default — and a column default only applies when the column is omitted. So a client-supplied id is accepted as-is:

Tableid typeDefaultClient can supply?
social_postsuuiduuid_generate_v4()Yes
sim_direct_messagesuuiduuid_generate_v4()Yes
chat_messagesuuiduuid_generate_v4()Yes
sim_emailsuuiduuid_generate_v4()Yes

So: crypto.randomUUID() on the client, send it as id, reconcile with m.id === payload.id. That one change lets you delete the ~160 lines of content-string matching in ChatInterface rather than replicate it. Validate the id is a well-formed uuid server-side and let the primary key reject replays.

RISK-06 The profile cache collides with a live role-change flow Medium

server/routes/profile.ts:85 · become-trainer

With a 30–60 s cache keyed by user id, a freshly upgraded trainer keeps participant-level UI until it expires. Confusing, not dangerous — the staleness is toward less privilege and authorization stays server-side.

But the cache is per-container, and Render may run several. Invalidating on the container that handled the update does nothing for the others.

Resolution — skip the cache entirely

Put the role in Supabase app_metadata, which travels inside the signed JWT and is server-controlled. AuthContext.tsx already documents this as safe but unused:

From the codebase: "app_metadata.role is server-controlled and safe to honor if present, but it is currently unused, so the backend profile is the source of truth."

With the role in the token, requireAuth needs zero database lookups once local JWT verification lands — no cache, no TTL, no multi-container divergence, and one fewer round trip than even the cached version. Requires writing app_metadata.role wherever the role changes, and calling refreshSession() client-side so it takes effect immediately rather than at token expiry.

RISK-07 Compression touches binary and streaming paths Low, but verify

  • NDJSON war-room builds use res.write + flushHeaders(). Compression buffers, stalling stage-by-stage progress. Must be excluded, not merely tuned.
  • tileProxy returns already-compressed image/png buffers. The default compressible filter should skip them — verify rather than assume.
  • Content-Length is replaced by chunked encoding. No client reads it today; grep before shipping.
Resolution — no route list to maintain

The streaming routes already send Cache-Control: no-transform, which is the standard HTTP header meaning "do not compress me". Key the filter off it rather than hard-coding paths:

app.use(
  compression({
    filter: (req, res) => {
      const cc = res.getHeader('Cache-Control');
      if (typeof cc === 'string' && cc.includes('no-transform')) return false;
      return compression.filter(req, res); // also skips images via `compressible`
    },
  }),
);

warroom.ts L389–395 does not set no-transform today — add it there so the filter covers both streaming routes automatically.

CLEAR The consumer audit for the slimming changes came back clean Verified

I specifically looked for things that would break when the two card endpoints get narrowed, and found none beyond what the plan already lists:

  • No server-side code consumes either list endpoint.
  • loadtest/session.ts only POSTs and PATCHes sessions; it never reads the list.
  • No script in scripts/ or demo_scripts/ consumes them.
  • ScenarioDetailView refetches the full row by id, so detail editing is unaffected.
  • The engagement engine reads scenarios.initial_state directly server-side, not via the list, so background engines are unaffected.

The one real dependency remains ExpandedPoster's use of initial_state.stakeholders, which the plan already handles.

New issues the Part 3 fixes can cause (added 24 Sep 2026)

I checked the index and archive fixes against the live project before recommending them. The indexes are low-risk. The archive job carries more risk than it first appeared, and two of these would have shipped real problems.

RISK-08 An archive table would be readable with the public key Security

Default privileges on schema public

Measured on this project: every new table created in public automatically grants the public roles (anon, authenticated) permission to read, insert, update, delete and truncate it. The live tables are only safe because each has row-level security switched on, most with zero policies, which means deny-all. But copying a table's structure (CREATE TABLE … (LIKE …)) does not copy its row-level security. The public key ships inside the app, so a plainly created archive table would expose every archived post, message and state snapshot to anyone, for reading and for writing.

Views have a trap of their own. A plain view that combines live and archive rows runs with its owner's rights and ignores row-level security, so it would expose the live tables as well.

Resolution 
create schema if not exists archive;          -- not exposed through the API
create table archive.social_posts (like public.social_posts including defaults);
alter table archive.social_posts enable row level security;
revoke all on archive.social_posts from anon, authenticated;
-- and any combined view:  create view ... with (security_invoker = true)

Do this in the same migration that creates the tables, before any data is copied in.

RISK-09 Archived exercises would go blank on most screens High

The first draft of the archive plan listed five places that read finished exercises. But any API route that takes a session id can be pointed at a finished exercise, whether by review mode, the trainer dashboard or an old link. The events table alone is read in 35 server files, including routes like events.ts, sessions.ts, decisions.ts and injects.ts. After archiving, every one that still points at the live tables silently shows an empty exercise.

Resolution — pick one

(a) Repoint every reader to a combined view, which is the largest change. (b) Restore on open: when someone opens an archived exercise, move its rows back first. No code that reads the data has to change, and the first open takes a few seconds. (c) Archive only after the review window, and make the after-action review the only supported view of an archived exercise. Recommended: (b). This is open question 10 in the plan.

RISK-10 The index migrations can't run through the normal migration path Medium

Building an index without blocking writes (CREATE INDEX CONCURRENTLY) cannot run inside a transaction. But Supabase's migration tooling applies each file inside one, and pasting a multi-statement file into the SQL editor runs it as one too. No migration in this repo has ever actually done it: migration 108 only mentions it in a comment. If a build fails partway, it also leaves an invalid index that slows every write but is never used.

Resolution

Run each CONCURRENTLY statement on its own, one per SQL-editor run. Or, when no exercise is running, use a plain CREATE INDEX, which works in the normal runner and blocks writes to that one table for only a few seconds. Before any retry, check select indexrelid::regclass from pg_index where not indisvalid; and drop what it lists.

RISK-11 Disk space goes up before it comes down Medium · cost

Copying before deleting means both copies exist at once, so the first full run needs roughly 1.2 GB of extra disk, the combined size of the per-exercise tables. Deleting rows also doesn't give space back on its own: the live tables keep their size as mostly empty pages until the space is reclaimed. Disk growth is billed and may not shrink back by itself. And on smaller Supabase compute sizes, disk throughput is limited, so big jobs like index builds, the first archive run and a repack can slow everything else while they run.

Resolution

Check disk headroom in the Supabase dashboard first. Reclaim the space once after the first run with pg_repack (available here, not yet installed), which works mostly online. Run all of it off-hours, and watch the Disk IO metric while it runs.

RISK-12 A big exercise means a big, noisy transaction Medium

Archiving the 54,865-post exercise in one transaction would hold locks and write a large burst of change records. session_events is also published to Supabase Realtime, so a mass delete is a burst Realtime has to process, which could delay live chat and incident updates if it runs during an exercise.

Resolution

Move one table at a time, and record a state on the exercise (copying → copied → deleting → archived) so a failure midway can be re-run safely. Run it off-hours. A free win on the side: nothing subscribes to session_events through Realtime (no frontend or server subscription), so removing it from the Realtime publication would stop that processing for every event insert. Confirm that first.

RISK-13 The 99.94% figure is a lifetime average Low · measurement

These counters have never been reset, so the hit rate blends months of history and could hide a recent decline. The obvious fix, resetting statistics with pg_stat_reset(), is the wrong one: autovacuum relies on the same counters to decide when to clean tables.

Resolution

Save blks_hit and blks_read once a week and compute the rate over the difference between snapshots.

CLEAR No link between posts crosses exercises Verified

If a reply or repost pointed at a post in another exercise, archiving one exercise at a time would break that link. I checked: 0 replies and 0 reposts cross exercises (only 10 reposts exist in total), so per-exercise archiving is safe on that front.

What none of these fixes address

The engagement tick is itself an over-fetch

runEngagementTick does select('*') over a 45-minute window, then issues one UPDATE per post, serially, every 30 seconds. On a busy session that's hundreds of round trips per tick, competing for the same database and buffer cache the feed fix is trying to exploit. Probably the largest remaining background-load problem once this plan lands.

select('*') will keep coming back

Slimming two endpoints fixes two endpoints. The root cause is that insider_knowledge and current_state sit on hot rows. Until they move to side tables, every new query is one select('*') away from re-creating the same bug somewhere else.

Section 07

What is already correct — do not "fix" these

Just as useful as the bug list. These look like problems, or are places someone would naturally start optimising, and they are fine. Time spent here is wasted.

Correct All expensive AI work is already non-blocking

Post grading, media generation, NPC DM replies and NPC email replies all use void (async () => …) fire-and-forget. Nobody waits on a language model. This is genuinely well built.

Intentional The 3–10 second NPC reply delay

socialMessenger.ts:279 deliberately randomises a delay so NPCs don't reply inhumanly fast. That is realism, not latency. Leave it alone.

Harmless The "unbounded" likes and flags queries

These query by player_id with no session filter, which looks alarming. The tables hold 140 and 147 rows in total. Ignore them.

Fine Indexes on sessions / session_participants

Technically missing, genuinely irrelevant at 265 rows — the planner scans them in 0.4 ms. Adding indexes would cost writes and buy nothing.

Fine Card artwork and lazy loading

30–50 KB WebP thumbnails with loading="lazy" on the main grid. Only three stray <img> tags need the attribute added.

Fine Row shape of social_posts

No fat JSONB column; ~1,399 bytes per row. Column pruning here — the fix that worked so well in Part 1 — would achieve almost nothing.

Not needed yet A bigger Supabase compute size

99.94% of reads already come from memory, above Supabase's 99% healthy mark. The waste is in specific queries (Part 3), not a lack of memory. Upgrade only if that rate drops below 99%.

Not needed Moving heavy columns into side tables

Postgres already stores current_state and insider_knowledge out of line. The sessions table's main storage is 128 kB, with 7 MB held separately. Explicit column lists plus a lint rule get the same benefit without a migration.

Section 09

How we prove it worked

Capture a baseline before touching anything, or the improvements are assertions rather than facts.

  1. Payload sizes. curl -s -o /dev/null -w '%{size_download} %{time_total}' against the scenario list, session list and feed endpoints — with and without Accept-Encoding: gzip, authenticated as a trainer.
  2. Bundle size. Record frontend/dist/assets sizes plus the gzipped entry chunk. Add rollup-plugin-visualizer for a before/after treemap.
  3. Query plans. EXPLAIN (ANALYZE, BUFFERS) on the feed query for the busiest session, both cold and warm. Distinguish them by comparing read= versus hit= in the buffers line — the cold number is the one users feel.
  4. Time to first card. DevTools performance trace of a cold /dashboard, /scenarios and /sessions. Record time-to-first-card, total transferred, and main-thread JSON.parse time.
  5. Keypress to visible. Trace sending a DM and posting a reply. Measure from keypress to the message appearing. After Fix 6 this should be a single frame.
  6. Main-thread profile of a two-minute window in a live session with realtime active, before and after the logging cleanup.

Regression surface

The slimming changes in Fix 1 touch shared endpoints, so exercise all of it: scenario library (every filter, all four sort orders, search by title / description / category / organisation / country, card and list views, expand, delete, launch), the create-session modal, the sessions page (all three groups, status filter, start session, open lobby, view AAR), trainer dashboard tiles, participant (non-trainer) views of both pages, and the trainer scenario detail view including the insider_knowledge doctrine editor.

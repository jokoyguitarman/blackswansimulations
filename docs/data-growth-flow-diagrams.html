Two words used throughout. Fast memory is the database's desk: anything already on it comes back instantly. Disk is the filing cabinet in the back room: anything in there needs a slow trip. Diagram 1

The life of an exercise's data

While an exercise runs, the game writes into several tables at once: a full snapshot of the scenario state every time it changes, every post and reply, every event, and every 30 seconds the engagement engine rewrites post scores and logs each change. When the exercise ends, nothing happens to any of those rows. They stay in the same tables the next exercise writes into, so the tables only ever grow. Right now, every row in these tables belongs to an exercise that has already ended.

Drawing diagram…

Fix spot

Right after step 4, the moment an exercise ends. That is the natural point to move its rows out of the live tables (Fix 3, detailed in Diagram 6). Today there is simply no step there, so the answer to "what happens to this exercise's rows?" is "nothing".

Diagram 2

    
How the database fetches data (the desk and the filing cabinet)

    
The database never fetches a single row. It fetches whole 8 KB pages, each holding many rows. Every page is either already in fast memory (a hit) or has to be read from disk (a miss). On your own feed query, a hit cost about 0.01 ms per page and a miss about 0.9 ms, roughly 80 times slower (88 ms for 7,456 pages warm, versus 6,811 ms when 7,357 of them came from disk). When memory is full, something has to be thrown out to make room. The more pages there are competing for the same memory, the more often the page you need has been thrown out.

    
Drawing diagram…

    

      
Three fix spots on this diagram

      
Need fewer pages per request (the feed as one database function: 7,456 pages down to 1,203; and the new indexes in Diagram 7). Have fewer pages competing (Fix 3: archive finished exercises so the live tables stay small). Make the desk bigger (Fix 2: a larger server) is not needed yet: 99.94% of reads are hits today. Only upgrade if that drops below 99%.

Diagram 4

    
What select('*') actually does, on the Sessions page

    
The database already keeps big values, like each session's 209.5 KB current_state, in a separate storage area and leaves only a small pointer in the row. So a query that doesn't ask for them never touches them. select('*') means "every column", so the database follows every pointer, fetches every big value, unpacks it and ships it, even though the page only shows a status, a time and a title.

    
Drawing diagram…

    

      
Fix spot

      
Step 2, the query itself (Fix 1). Asking only for the columns the page shows means steps 4 to 7 never happen: about 9 KB comes back instead of 8.2 MB. No database change is needed, because the big values are already stored separately.

Diagram 5

    
Why select('*') keeps coming back

    
Fixing one query does not stop the next one. select('*') is the easiest thing to type, it looks harmless in review, and it is fast at first because there is little data yet. It only turns slow weeks later, when nobody remembers why. The loop below only breaks if the check is automatic.

    
Drawing diagram…

    

      
Fix spot

      
At the commit, before the code ever ships (the rest of Fix 1). Your pre-commit hook already runs ESLint on server code with zero warnings allowed. Adding one rule that rejects select('*') on the sessions and scenarios tables means a new offender cannot even be committed.

Diagram 6

    
Fix 3 in detail: archiving a finished exercise safely

    
This is the job that fills the empty step in Diagram 1. It runs off-hours, one finished exercise at a time, and moves that exercise's rows into matching archive tables. Two things must be in place before the first run, and the order of the steps is what makes it safe. Checking this design against the live project turned up three ways it can go wrong, shown as the red paths.

    
Drawing diagram…

    

      
Red path 1 · wrong order destroys after-action data

      
Likes, flags and the engagement log are set to delete themselves automatically when their post is deleted. So "just delete the old posts" silently wipes every like, flag and engagement record with them. The job must copy those rows to the archive first.

    

    

      
Red path 2 · a plain archive table is readable with the public key

      
On this project, every new table automatically gives the public roles permission to read, change and delete it, and copying a table's structure does not copy its row-level security. The public key ships inside the app, so a plainly created archive table would expose every archived post and message to anyone. The archive tables must be created with row-level security switched on, before any data goes in.

    

    

      
Red path 3 · archived exercises go blank

      
Far more code reads finished exercises than the after-action review: the events table alone is read in 35 server files, including routes that review mode and the trainer dashboard call. Any screen that still points at the live tables shows an empty exercise. Restore on open (move an exercise back when someone opens it) avoids changing any of that code.

Diagram 7

    
The statement watchdog reads every finished exercise to find the current one

    
During every exercise, the statement watchdog keeps asking for "this exercise's oldest 100 official and player posts". There is no index on exercise + time, so on a large exercise the database walks the whole table's time index from the first post ever written, discarding every other exercise's posts until it reaches this one. On your busiest exercise it discarded 104,364 posts each time: 85,545 page reads and 576 ms per scan. It also gets slower with every exercise you run, because the history in front of the current one keeps growing. This is the clearest case of old exercises' data being read for no reason.

    
Drawing diagram…

    

      
Fix spot

      
Step 2. Add an index on social_posts (session_id, created_at), replacing the plain session index, so the database jumps straight to this exercise's posts in time order and stops at 100. The events table gets the same treatment (session_id, event_type, created_at): it sweeps every exercise's events of a type in the same way, and it is the table read most from disk. A third, tiny index on original_post_id stops every post deletion from scanning the whole table (902 ms each today).

    

    

      
The trap (the red path on the right)

      
"Only read posts since this exercise started" looks like a one-line fix, and it measures well (10.7 ms). But 2,458 official posts are deliberately backdated up to 30 days, to give each organisation's page a pre-crisis history, and the watchdog reads official posts. That condition would silently hide them. The index fixes the speed without changing what the watchdog sees.

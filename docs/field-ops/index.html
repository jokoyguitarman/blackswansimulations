1What this set is

The user journey document says what field operations should become and why. This set says how to build it: exact migrations, API contracts, file maps, component states, LLM contracts, tests, flags, commit plans and acceptance criteria, precise enough to hand to a coding agent. The UI mockup shows what it looks like, and the UI spec sheet maps the mockup element by element.

3Handing work to a coding agent

  1. Give the agent the master plan and the one workstream spec it is building. Together they hold every name, number and contract it needs.
  2. Name the task by its id (for example T3.2). Each task lists its files, steps, the observable done-when and the tests to add.
  3. Ask for one commit per row in section 13 of the spec. Each commit has its own backtracking step.
  4. Before merging, run node scripts/verify-field-ops-specs.mjs if a spec changed, and npm test plus npx tsc --noEmit if code changed.
  5. If the work needs a name, flag, migration number or route that the spec does not allocate, stop and change the master plan first.

A prompt that works as a starting point:

Implement task T<ws>.<n> from docs/field-ops/<spec>.md.

1. Read docs/field-ops/00-master-plan.md and the spec first. Use only the flag names, migration numbers,
   route prefixes, type names and component names the master plan allocates.
2. Do exactly what the task lists: its files, its steps, its tests. Do not touch other files.
   Where the spec cites existing code, open it and confirm it still matches before changing it.
3. Everything new stays behind its flag, and the legacy behaviour must be unchanged with the flag off.
   A migration must be additive, and the code must work before the migration is applied.
4. Add every new test file to the test script list in package.json.
5. When finished, run npm test and npx tsc --noEmit, then report which of the task's done-when
   conditions you observed and how. If something in the spec is wrong or missing, say so instead of guessing.

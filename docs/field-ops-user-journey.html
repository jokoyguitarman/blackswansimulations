What field operations is. A trainer (an independent consultant) uses the War Room wizard to describe an emergency — today, a bombing — lay out a real building on a map, and let AI build a complete exercise: response teams, a timeline of events (“injects”), hazards that worsen if ignored, casualties to triage, hidden bombs to find, an adversary to track, and a rubric. She then runs it live: participants join by link (no account needed), take team roles, coordinate through a shared map, chat and voice, and type decisions that a pipeline of AI evaluators judges; a 30-second engine in the API process drives the clock. When it ends she asks for an After-Action Review.

The shape of the code. React 19 SPA → one Express + Socket.IO process on Render that also runs every background engine → Supabase (using the service-role key, so route code is the only authorisation) plus OpenAI/Bedrock, Stripe and OpenStreetMap. Data has three lifetimes: draft → scenario (template) → session (clone).

What it can do

Build

A resumable, credit-metered wizard. A scene editor with real OSM buildings (or hand-drawn / auto-traced footprints), blast and weapon, six hazard types, exits, walls, planted devices and crowd size. AI-written research and doctrine per team. Compile produces ≈ 28 timed + ≈ 16 conditional injects, hazards with deterioration and child spawns, ≈ 35 casualties, hospitals/police/fire POIs, routes, equipment, a pursuit tree with gates, insider dossiers and a fire/smoke simulation.

Run

Guest join links, email invites, a team matrix and ready-check; Start clones the world into the session. Live: scheduled and AI injects, escalating hazards, deteriorating patients, claims/tagging/asset placement (on the interactive map), free-text decisions graded by AI with a heat meter, team/DM/Insider chat, peer-to-peer voice, notifications, a trainer cockpit, and a demo mode with AI-controlled teams.

Learn

Complete → Generate AAR (on request): an AI narrative or a 14-section report, team heat, participant coordination/leadership, a pursuit-intelligence timeline, PDF and Excel export. No overall score, no replay.

Eight things to know before you touch it

  1. One process runs everything. API, sockets, voice registry and all engines. Never run a second copy with engines on; a Render deploy briefly does exactly that (18.1).
  2. Authorisation is hand-written and the service role bypasses RLS. A new route that forgets a check is a hole; the helpers exist (lib/access.ts) but nothing forces their use (17.1).
  3. The browser hides what the API sends. True triage colours, planted devices, zones, evaluator verdicts and other teams’ chat reach every client (13.2, 14.1).
  4. Template rows vs. session clones. Hazards and casualties are cloned at Start; scenario_locations, equipment and the scene are shared, so editing them mid-exercise changes every live session (8.5).
  5. A team is a string. Injects, counters, equipment and the bomb-squad logic match on the name — there is no foreign key (3.2).
  6. sessions.current_state is one JSON blob read-modify-written by many writers, so updates get lost (12.2, 15.2, 11.1).
  7. Compile is one 2–10-minute request with ≈ 100 LLM calls, a credit spent first, no transaction and no lock (7.1, 7.3).
  8. The risky code has no tests, and the big files are huge. 14 field-ops files exceed 2,000 lines; none of the generator, Start, the scheduler, any route or any authz helper is tested (18.4). Write characterisation tests before refactoring.

The browser talks to the Render API directly (VITE_API_URL), not through Vercel. api/index.ts is a stale, partial Vercel-function copy of the Express app (no war-room or scene routes; its own header says WebSockets can’t run there) — it is not the production path.

The three data lifetimes

1 · Draft

warroom_wizard_drafts — the wizard’s working memory: choices, geocode result, research, doctrines. One row per scenario-in-progress. Disposable.

2 · Scenario (template)

scenarios + child rows with session_id IS NULL: teams, injects, hazards, casualties, locations, equipment, gates, objectives, plus rts_scene_configs. Reusable “sheet music”. Editable until a session is live.

3 · Session (clone)

sessions + cloned hazards/casualties with a session_id + current_state JSON + placed_assets, chat, decisions, events. Everything players change lives here.

Cloning happens at Start (Chapter 11) — and not for everything: scenario_locations stay shared at scenario level, so editing a pin mid-exercise changes every live session of that scenario.

Build the exercise

Eight steps, all inside the War Room wizard and the scenario library. Everything here happens before a single participant joins. The output is a scenario: a reusable template that live sessions are later cloned from.

01

Enter the War Room

Gates, credits, drafts — and the choice between “teams on the ground” and “teams on the phone”.

Trainer / Admin/warroompages/WarRoom.tsx · step 0

The story

Aisha is a consultant who runs crisis exercises for clients. She signs in and opens War Room. Three things can happen before she sees the wizard:

  • If her profile isn’t a trainer: “Access denied — War Room is available to trainers only.”
  • If she hasn’t submitted her signed Consultant Agreement, the app keeps redirecting her to /apply (the only pages open to her are /apply and /account).
  • If she has 0 scenario credits (and isn’t an admin) she hits a full-screen wall: “Scenario generation requires a paid engagement” with a Go to Clients & billing button. This is the business model in code: she invoices a client from the Clients page; when the client pays, the Stripe webhook grants 1 scenario credit + 2 session credits. A scenario credit is spent at the very end of the wizard (Compile); session credits are spent when she creates sessions (Chapter 9).

Past the gates she sees a dark hero, “What are you training for?”, two counters (drafts saved / compiled) and — if she has any — a glass panel “Pick up where you left off”: her 20 most recent drafts, grouped In progress and Compiled, each with a tick-bar, step name, last-updated time and a Resume (or Re-compile) button.

Two large cards sit below: Field operations — “Teams on the ground” (bombing, armed attack, CBRN; a real location, a scene she lays out, hazards and casualties that evolve; ~20 min to build) and Corporate crisis — “Teams on the phone” (feeds, inboxes, stakeholders — a separate wizard, out of scope here). She picks field operations and presses Continue.

That click quietly creates a draft row and puts ?draft=<uuid> in the URL. From now on the page shows a stepper (Mode · Incident · Teams · Scene Editor · Location · Research · Compile), a “Scenario so far” panel and a sticky bottom bar with Back, Save draft and a primary button whose label changes per step (Suggest teams → Lay out the scene → Check location → Run research → Compile). Every Next/Back/Save writes the draft, so she can close the laptop and resume tomorrow.

02

Choose the incident

Which kind of attack? Today that really means “which kind of bomb”.

TrainerWarRoom.tsx · step 1scenario_templates/scenario_types/*.json

The story

The hero asks “What kind of incident?” Four groups of tiles: Explosives — Bombing (General), Car Bomb / VBIED, Suicide Bombing, Mall Bombing — are live. Armed Attack (open-field shooting, knife attack), CBRN (chemical/gas, poisoning) and Other (kidnapping/hostage, hijacking) are greyed out with a Soon tag. Each live tile has a one-line hint (“Placed device · blast & fragmentation”, “Vehicle-borne · secondary device sweep”, “Person-borne · crowd egress”, “Enclosed retail · multi-level evacuation”).

Beneath the tiles is a dashed box: “Or describe your own — Anything explosive-based works today — the type is inferred from what you write”, with a text field and a placeholder like “IED hidden in a vehicle outside a government building during a state visit…”. Picking a tile clears the custom text; typing custom text deselects the tile. The “Scenario so far” panel shows her choice and the button reads Suggest teams.

Under the hood

The incident type is just a string, scenario_type, but it is load-bearing: it selects scenario_templates/scenario_types/<type>.json, which supplies the required teams (Ch. 3), the per-team counter definitions (the live KPIs each team sees), the condition keys that conditional injects can use at runtime, and the default threat profile (weapon class, scale) that sizes the casualty count. The wizard also hard-wires setting = "office" and terrain = "urban" (warroomService.ts:322-324) — there is no UI to choose a different setting.

A2 · 24 Oct 2026 · the incident screen becomes one setup screen

The screen above, and the team, location and research screens after it, are being replaced by one setup screen fed by the trainer’s own scenario document. A1 still holds: a type we have not built is named and stops. What was decided:

  • The trainer’s document is uploaded on the setup screen and prefills the incident, device, location, responding agencies, pressure bodies and adversaries. Anything the document leaves out is generated and marked as generated.
  • Each team is matched to a doctrine in a shared library. When none is found the trainer writes one on the spot. It is shared with every trainer at once and marked Unverified until an admin approves it.
  • The similar-cases research is removed, and per-team standards research is replaced by the library. Device effects come from a library first and from the LLM only when nothing matches, always labelled.
  • Each agency has a roster of roles and is run by people or by AI, built on the corporate teammate-bot framework with the doctrine as its planner.
  • The trainer can lay out the scene while a team has no doctrine, but compile is blocked until every team has one.

The design, the mockup, what we verified in the database and the order of work are in Addendum · Document-driven setup.

A3 · 24 Oct 2026 · the site is set on the setup screen, and devices become detailed

Two decisions refine A2.

  • The site is set on the setup screen, from the saved map data. The trainer searches a landmark or street and a dropdown offers matches from the saved OpenStreetMap tables in Supabase. Picking one centres the map, defaults the radius to 150 m, and outlines the building, its neighbours and the streets the way the Scene Editor’s first screen does today. She can expand or shrink the radius, click other footprints to mark more buildings as involved, and draw or trace a building the data lacks. Nothing involves Google Maps, and no building, road or address data is fetched live.
  • Lay out the scene opens with the site already loaded. No searching, no coordinates, no radius, no picking or outlining the building again. It is where the trainer adds hazards, walks the site taking photos, plants the devices and places exits and walls.
  • A device can be described in as much detail as the trainer wants. Explosive and quantity, fragments and casing, other hazard materials, how it is initiated and wired, the container and where it is. Every field is optional. What she enters is used exactly as given in the blast, damage and casualty calculation; what she leaves blank is assumed from the incident, the container and the venue, and labelled as assumed.
  • Addresses will work. The saved map data is re-extracted with street numbers and postcodes, so the dropdown can resolve an address as well as a landmark or street.
  • Other involved buildings are handled at footprint level. They appear on the map, devices and hazards can be placed in them, and exits and wall points are generated from the footprint. Only the primary building gets the full interior layout.
  • The crowd is split. The headcount is set on the setup screen, because documents usually state it; where people stand is painted as crowd zones in Lay out the scene.

Still open and listed in the plan: what happens outside Singapore, and whether trainer photos alone replace Street View.

The plan in one page

Today. Aisha builds a field-ops exercise across five separate screens, and the system only understands her teams if they are one of eight names it already knows (3.2). The plan. Aisha starts by dropping in her document, or typing a description. Compile builds the exercise from three things — her document, the doctrines, and the physics calculated from her device details — with no research step. Design 1 · Teams, archetypes and doctrines

Build spec: 02 · Teams and doctrines.

A team stops being a name and becomes five connected things. Everything else in the plan sits on this.

Team card

One unit players join: a name, an optional agency label, a description the trainer can rewrite freely, minimum and maximum players, the investigative switch, people or AI, and its doctrine.

Archetype

What kind of team it is, from a closed list. It starts as the eight the system already knows (Evacuation, Hazards / Fire / Rescue, Medical Triage, Media & Communications, Bomb Squad / EOD, Pursuit & Investigation, Incident Command, Police / Security) and grows: Transport Operator, Venue Operations, Hospital, Utilities, Ministry liaison. Each has aliases (SPF, SCDF, EOD…).

Capabilities

What the platform lets that archetype do: map actions, assets it may place, KPI counters, equipment, zones it may enter. Today these are spread across keyword matches. A new archetype starts as “talk and decide only” and gains capabilities as they are built.

Doctrine

The rulebook: mission, response sequence with time targets, a never-do list, hand-offs to other teams, what good looks like (used for scoring), and where it came from.

Roster

The roles players take inside the team (Incident Commander, Cordon Lead, Crowd Officers…) with how many of each. Labels and seats first; permissions such as “only the commander authorises” are an open question.

How a team is matched to a doctrine
  1. Alias table (deterministic, free): “SPF”, “Police”, “Singapore Police Force” all resolve to Police / Security.
  2. Name and description against archetype names and doctrine titles in the library.
  3. AI layer: given the team’s name, its description and the sentence in the document, it ranks the closest archetypes from the closed list (it cannot invent one) with a confidence and a reason.
  4. Thresholds (starting values, to tune): 85 % or more is assigned and shown as “matched 96 % — change”; 60–85 % is suggested for the trainer to confirm; below 60 %, or no doctrine yet for that archetype, shows No doctrine detected.
When no doctrine is detected

The card turns amber and the drawer explains, in plain words, what a doctrine is: the rulebook a team plays by, used to build the scenario, to judge players and to drive AI teams. Aisha can start from the closest doctrine, begin blank, or tick Draft it for me: the AI proposes every field from the team’s description and her document, she edits, and it is saved as AI-drafted. Two buttons finish it: Save to library & use (shared at once, Unverified) or Use in this scenario only (a private copy). She can keep laying out the scene meanwhile; compile waits until every team has a doctrine. (See the mockup, state 2.)

Added 3 Nov 2026 · Doctrines by country

Grouped by country and agency. Singapore’s police doctrine and Malaysia’s are separate entries, each tied to its country and agency, so the right one is found for the right team. The library is seeded once, during development, with the doctrines of the main response agencies of the Southeast Asian countries: police, fire and rescue, civil defence, medical services, bomb disposal and disaster management. They are researched from public sources, each with a source note, and reviewed by a person before they are marked Verified; restricted or classified material is never used. Like the saved map data, they are loaded from the database when a scenario is built, and nothing is researched then. Matching uses the agency’s country, taken from the trainer’s words or from the site.

When a named agency matches nothing, Aisha has three ways in: pick any doctrine from the library (any country) for that team, type one into the doctrine fields, or upload a doctrine document for that agency, organisation or team. Whichever she chooses, she says which country it belongs to. An uploaded document is read into the doctrine’s fields for her to check, and it joins the library as Unverified. These are decisions D29 and D30 in the master plan; spec 02 is revised before it is built.

Which value wins
  1. Yours. Whatever she entered is used exactly as given.
  2. Library default. For each blank, the library’s typical value for that device class and venue, and the published TNT-equivalence factor for each explosive.
  3. UpdatedLibrary rule. Every remaining blank has a rule in the library, so no model is ever asked for a device value. A model only reads a container or size category that the trainer’s own words state. (This page first said the LLM would propose a value inside hard bounds.)
  4. Always labelled. Each parameter shows its origin (Yours · Library · Assumed) on the device card, in the scene and in the After-Action Review. Nothing is silent.
How the effects are calculated

Deterministic code, no LLM. The charge becomes an effective TNT-equivalent mass; published scaled-distance relationships give peak overpressure and impulse against distance; the placement adds confinement and surface reflection; published blast-injury thresholds (eardrum, lung, lethality) turn that into bands; fragment mass and type give a fragment range; fuel or gas gives a thermal radius. The result is the bands in metres, the fragment range, the structural effect and the injury mix, shown beside the inputs that produced them. Casualties then come from who is standing where: people per zone, how much of each band covers the zone, and what the walls shield. That replaces today’s fixed 33 % and 66 % bands and the single “Pedestrians” tier.

It runs on the server, so setup, the Scene Editor and compile show the same numbers. Setup shows a preview that assumes the venue’s usual confinement; the final values appear when the device is planted.

Guard-rails

A plausibility check of the quantity against what the container can hold (a warning, not a block). Hard bounds on every assumption. One blast model replaces the three that coexist (7.11). The trainer can override any output, including the radius, and manual values are flagged in Review. A subject-matter expert reviews the calculator and it is checked against published reference data (response-planning stand-off charts, blast-effects handbooks) before anything is called Verified.

What the form is, and is not

It captures what the simulation needs: categories, quantities and notes. It never asks for, produces or stores assembly instructions, and the AI never expands a trainer’s entries into construction detail. Wiring notes are scenario facts for the bomb-squad exercise. If a model declines to help with an input, the trainer enters the values by hand.

The library holds typical devices per class, the published TNT-equivalence factors, the injury thresholds and the reference distances. The 16 research_cases are kept as a cross-check, not as truth: an LLM wrote them. Every entry is reviewed by a person and nothing is Verified by default.

Added 3 NovThe library also stores how things burn and break: how each material ignites and spreads fire, how much smoke it gives off, how walls and floors resist fire, and how gas and smoke plumes behave. Compile and the live world of Design 7 read these values, so nothing is researched for a scenario. This replaces today’s model call that “researches” deterioration physics for every compile (D31).

Press Start

One PATCH flips the session live, clones the scenario into the session, and hands the clock to the engines.

TrainerSessionLobby.tsx · handleStartSessionPATCH /api/sessions/:idsessions.ts:1391-1640

The story

When the readiness bar is full, Aisha presses Start session (the button is disabled until every participant is ready; the Start button on the Sessions page has no such check and no confirm). The request takes a few seconds — it initialises state and makes an AI call before it returns. Then her page becomes the live exercise: a header reading “Status: IN PROGRESS”, a ticking elapsed clock and a Complete Session button. Every lobby receives a session.started event (or notices within the 5-second poll) and swaps itself for the live UI. The first time-based injects arrive on the next scheduler tick — within 30 seconds.

Under the hood

Start is not a separate endpoint — it is the branch status === 'in_progress' && !session.start_time inside the generic PATCH /api/sessions/:id. In order:

  1. Set start_time = now().
  2. Re-sync current_state = {…current, …scenario.initial_state} (the trainer may have edited the scenario since the session was created).
  3. cloneScenarioPinsForSession — copy the scenario’s template casualties and hazards into session-owned rows (so each exercise mutates its own copy), reset scenario-level sighting pins, copy sweep_device_pool.
  4. initializeSessionObjectives (progress 0) and initializeSessionGateProgress (so the scheduler and gates work).
  5. loadAndApplyEnvironmentalState — team-state containers from each team’s counter_definitions, _counter_definitions, route locations into environmental_state.routes; writes sessions.current_state and emits state.updated.
  6. UPDATE sessions with the updates object built at step 2.
  7. If AI is on: identifyEscalationFactors (an awaited LLM call) → session_escalation_factors.
  8. Broadcast session.started; ping the teammate-bot hook (a no-op for field ops).

Each init step is try/catch-and-continue. There is no scheduler registration: the engines (Ch. 12) simply poll for sessions with status = 'in_progress' AND start_time IS NOT NULL — but only in a process started with RUN_BACKGROUND_ENGINES=true (server/index.ts:85). Elapsed time is wall-clock since start_time. Complete sets end_time and snapshots scenario_state_history so counters survive for the AAR.

The three data lifetimes (worth memorising)

Draft (warroom_wizard_drafts) → Scenario (template rows with session_id IS NULL) → Session (cloned rows with a session_id, plus sessions.current_state JSON). Hazards and casualties are cloned at Start; locations are not — they stay shared at scenario level (which is why editing pins during a live session hurts, 8.5).

The clock: injects & the engine

Once the session is live, nobody “runs” the exercise: a 30-second heartbeat in the API process drives it.

EngineTrainerinjectSchedulerService.ts (2,159 lines · 30 s)aiInjectSchedulerService.ts (1,406 lines · 2 min)routes/injects.ts · injectPublishEffectsService.ts · conditionEvaluatorService.ts

The story — the first 60 minutes

Within 30 seconds of Start the first tick fires. It recomputes the live counters from the casualty and hazard pins (and pushes them as state.updated), runs any gate that is due, and publishes every scripted inject whose trigger_time_minutes has passed. Every due inject first passes an LLM “adversary” gate: it can cancel the inject (crediting the team’s heat meter) or swap in an adapted one. The gate is fail-open — if the model errors, the inject goes out as written.

A published inject becomes a timeline event, an incident card and a bell notification (universal or role-scoped only); media-type injects also create a media post. Field-ops injects never carry a delivery_config, so the email/feed/chat routing seen in corporate mode doesn’t exist here — everything arrives as an incident card. Pins reveal themselves through the read-time filter appears_at_minutes ≤ elapsed; unaddressed hazards escalate at +10 / +20 / +30 minutes (Ch. 13).

The surprise: the engine plays some teams itself. In every field-ops session — human-staffed or not — three deterministic “NPC queues” run each tick: the bomb squad auto-sweeps one un-swept asset per tick from minute 3; hazards get automatic “responses” from minute 5; and three patients are triaged per tick from minute 6 (Fire/Rescue handles HOT-zone patients, Triage handles WARM/COLD). They act through the same dispatcher the demo mode uses, creating decisions and chat messages “so sweeps are visible in the UI”. They key off the existence of a bomb / fire / triage team in the scenario, not whether a human is on it (12.1).

Other things that happen on their own: “Suspicious Package Report #n” tips (≈ T+8 onward) spawn a device pin, and a live device gets a 2-minute wall-clock fuse, then a detonation inject and 3–5 new casualties; each executed decision (human or NPC) triggers classification, flag flips and the heat meter, which yields a team-specific consequence inject; every 2 minutes an AI cycle computes the impact matrix and public sentiment and may publish universal or per-team injects (≤ 2 “friction” injects, plus an inaction penalty) — auto-published, with no approval queue; and at roughly 25 / 50 / 80 % of the duration the pursuit gates evaluate: met → an if_met inject, not met → a punishment or “vague” inject.

What the trainer can do: Start and Complete; the Injects card (“AI event injector”) lists injects with Publish (forced and repeatable, with no “already published” flag) and Create (writes a template-level inject that is always universal). There is no approve, edit, cancel or delay. There is no pause in the UI: the API accepts paused and the engines skip such sessions, but start_time never shifts, so everything overdue fires at once on resume (12.10).

The story

A decision in field ops is free text (a mic is optional). It can start from an incident card’s Decision button (linked to that incident; one decision per player per incident), as a pre-emptive decision, from a map-pin response ([Patient Response: …]), from a hazard assessment ([Hazard Response: …]), or from recorded map placements whose text is auto-composed. The Media team gets a four-part script editor for media_statement incidents (spokesperson, key facts, public guidance, closing). Every path calls POST /decisions and then immediately POST /decisions/:id/execute — the approval chain exists in the backend, but the UI always sends required_approvers: [], so it is effectively unused. There is no chat-based decision detection in field ops (that’s corporate-only).

Feedback. The AI verdict runs in the background and takes ≈ 10–60 s. Players never see a numeric rating. They see a live Heat Meter for their own team(s), in-world “field report” injects aimed at their team, and — for media statements — the editor’s verdict, score and feedback with a Revise statement button. The trainer additionally sees a per-decision AI badge (Meets Standards · Lacks Specificity · Below Standard · Issue · Rejected) with the reason, every team’s heat, and a backend-activity feed (AI steps and the inter-team impact matrix). There is no override, approve-rating or re-evaluate feature anywhere.

What a bad decision does. A forbidden action produces a critical “Action cannot be carried out” inject and +3 heat. Vague, contradictory, below-standard or prerequisite-failing decisions produce a team-targeted field_update inject that requires a response — escalating medium → high → critical with each repeat failure by that team (+1 / +2 / +1 heat). An LLM extracts explicit casualty orders from the text and rule checks apply: the HOT zone allows only extract or direct; WARM allows treat, direct, extract; COLD allows treat, transport, direct; a status chain must be respected. A violation fires a friction inject and nothing moves; a valid order sets the casualty moving. Hazards are not changed by text — they change through placed assets (resolved when an asset is within 80 m) and elapsed time. Heat sets the tone of the consequence inject: ≥ 60 negative, ≥ 30 mixed, below 30 positive.

Security & trust model

Most of the Critical and High findings in the earlier chapters share three roots. This chapter names them and lists the issues that belong to the platform rather than to a step.

The trust model in one paragraph

Who is trusted? Supabase’s verdict on a JWT — verified remotely, on every request (supabaseAdmin.auth.getUser; jsonwebtoken only decodes, for the limiter). user_profiles.role is trusted because only the service role or an admin can write it (a trigger in migration 189 blocks self-promotion; app_metadata.role wins over it when present). The service-role key is trusted completely: it bypasses RLS, so every authorisation decision is hand-written in access.ts, channelAccess.ts or inline. Not trusted: body, headers, params, user_metadata, socket payloads, and anything the UI hides. “Authenticated” is not “vetted”: anonymous sign-in is enabled (the join link uses it), so anyone can mint a valid JWT with the public anon key.

The three roots of most findings: (1) authorisation lives in ~300 hand-written route checks with no safety net — the helpers exist but are applied inconsistently; (2) a second authorisation plane — PostgREST, Realtime and Storage reached with the public anon key — is protected only by RLS, which is partial and inconsistent; (3) the UI hides things the API still sends (true triage colours, planted devices, zones, evaluator verdicts, chat from other teams).

What is solid (so this chapter stays honest)

Identity: tokens are validated server-side on every request, so revocation works; a missing profile means no role (fails closed); role self-escalation is blocked (migration 189 + prevent_role_self_escalation; sign-up sends no role; PATCH /profile role is admin-only); money routes re-check admin. Channels: one access rule serves REST and WebSocket; join_session checks membership. 17.2HighSecurity · Cost Rate limiting is effectively decorative

Happens
The global limiter keys on jwt.decode(token).sub — decoded without verification — and allows 10,000 requests per 15 minutes per key. (a) A random sub per request gives unlimited buckets. (b) Forging a known user’s id (user ids appear in rosters and voice events) exhausts their bucket and 429-locks a trainer mid-exercise. (c) The limit is so high that honest users effectively have none, and no AI route (compile, research, insider, Whisper, evaluation) has its own quota — so a single credit buys unlimited LLM spend (5.5, 14.11). (d) The one tight limiter, for joins, is 10/min/IP and shared by two calls per join (10.2). A valid-token flood from one user is still capped per user.

Key by IP (or token hash) before auth and by req.user.id after requireAuth; per-route quotas on every LLM endpoint; a per-session LLM budget (the unused budgetKey in chatClient.ts is the hook); CAPTCHA on anonymous sign-ins.

Infrastructure, performance & upkeep

How it runs, what it costs per click, why it can’t scale out yet, and why changes feel risky.

How it actually runs

One Render web service (documented as a single instance; no render.yaml or Dockerfile is committed) runs one Node process that is simultaneously the REST API, the Socket.IO server, the voice-call registry and all the background engines (Chapter 12). The SPA is static on Vercel and talks to Render directly. Supabase supplies Postgres, Auth, Storage and Realtime; LLM calls go to OpenAI (or Bedrock when AI_PROVIDER=bedrock). Deploys come from master; a Render deploy briefly runs the old and new containers side by side — exactly how the 20 Sep 2026 double-fire happened. During a long generation the server sat at ≈ 160 MB of 2 GB and < 2 % CPU: the machine is not the bottleneck; the single-process design and the database round-trips are.

What a click costs. Every authenticated request first makes two network calls — supabaseAdmin.auth.getUser(token) and a user_profiles lookup — before any work. The browser then polls: the lobby every 5 s (the whole session row, current_state averaging 25 KB, up to 273 KB), decisions every 5 s while an evaluation is pending, the AAR every 5 s while generating, the map every 30 s, the trainer’s activity feed every 8 s; and the engine broadcasts the entire state.updated to the whole room on every 30 s tick.

What was load-tested. loadtest/ (a field-ops, multi-session run on 2026-07-03 against the Render URL): 200 / 500 / 1,000 players in sessions of 100, 60 s per stage. WebSocket delivery was ≥ 99.9 % with no connect failures and ≤ 2 disconnects, delivery latency p50 ≈ 1.28 s (flat across load) and p95 ≈ 1.5–1.7 s. But the HTTP probe p95 was 2.3–2.6 s at every stage — above the test’s own 2 s threshold even at 200 players, which points at per-request overhead rather than load. The run exercised connection fan-out, not decisions, AI evaluation, map actions or generation.

C

Glossary

The vocabulary of the codebase, in plain words.

Scenario · Session · Draft

The reusable template; one live run of it with people; the wizard’s in-progress working copy.

Inject

A timed or conditional “something happens” message (a report, a call, a media item). Universal = everyone; team-specific = named teams. Timed, conditional, manual (trainer) or AI-generated.

State effect · Counter

An inject’s consequence on the world (e.g. slower flow). A counter is a live per-team KPI recomputed from pins every tick.

Gate

A checkpoint at ≈ 25/50/80 % of the exercise that fires one inject if a goal is met, another if not (used by the pursuit sub-game).

Pursuit · Sighting · False lead

The adversary sub-game for “investigative” teams: sightings appear as map pins (NATO-graded), some are false, and teams must commit resources to the true ones.

Hazard · Spawn pin · Deterioration

A fire, collapse, spill or suspicious package. Left alone it worsens at +10/20/30 min, spawning child hazards and casualties (spawn pins).

Casualty · Triage tag

A patient pin with a true colour (green/yellow/red/black) and a player colour once tagged.

Scene · Sim space · Stud

The trainer’s drawn building. Sim space = metres from the polygon centroid. A stud = a grid point (3 m live, 5 m at compile) that placements snap to.

Enrichment

Step 6’s analysis of the scene: per-hazard AI vision + a 60-minute fire/smoke simulation + synthesis.

Doctrine · Standards · Forbidden action

What “good” looks like for each team, per the AI; forbidden actions are things a team must never do (researched, then dropped, 6.2).

Insider · Environmental Truths

The in-game “person who knows” (LLM Q&A that unlocks map pins) · the trainer’s cheat-sheet of the real layout.

COP

Common Operating Picture — the shared map screen.

Heat meter

A per-team “how badly are you doing” percentage from the AI’s verdicts on decisions.

Robustness · Impact matrix

An LLM rating 1–10 of a decision’s resilience, re-computed every 2 minutes with cross-team effects.

NPC queue

The engine’s deterministic auto-play of the bomb-squad, fire and triage teams (12.1).

Credit (scenario / session)

Prepaid units: one to compile a scenario, one to create a session; granted when a client pays an invoice.

Edit lock

A scenario can’t be edited while a session is live or when the trainer has no session credits (enforced on only some routes, 8.5).

AAR

After-Action Review: the debrief generated on request after completion.

Service role

The Supabase key the server uses; it bypasses row-level security, so route code is the only gate.

Spectator / god view

A URL-parameter mode showing every pin with overlays; used for demos (and unguarded, 13.2).

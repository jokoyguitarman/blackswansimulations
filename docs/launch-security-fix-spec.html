01 · Storage

Media bucket

migrations/170_sim_media_storage_bucket.sql made sim-media public and added two policies. The live bucket is still public, and its size limit is now 500 MB. This fix must not touch the public flag or that limit.

What it does now

CREATE POLICY "Public read access for sim-media"
ON storage.objects FOR SELECT
USING (bucket_id = 'sim-media');

CREATE POLICY "Service role full access for sim-media"
ON storage.objects FOR ALL
USING (bucket_id = 'sim-media')
WITH CHECK (bucket_id = 'sim-media');

The first policy lets any caller with the public key list every file. The second is named for the service role, but it never checks the role. FOR ALL means select, insert, update, and delete, and an empty role list means everyone. The server does not need it. Uploads in mediaGenerationService, chatSurveillanceService, and socialCrisisWarroom already use the service-role key, which bypasses these policies, then store getPublicUrl() on the post.

A public bucket still serves a file to anyone who already has the URL. That is what the images in the sim use. Dropping the policies does not blank those pictures. It stops listing, uploading, overwriting, and deleting through the public key.

Replacement

DROP POLICY IF EXISTS "Public read access for sim-media" ON storage.objects;
DROP POLICY IF EXISTS "Service role full access for sim-media" ON storage.objects;

After this, the storage API refuses list, upload, and delete for anon and authenticated callers. The server keeps uploading. Existing public URLs keep loading.

Scenario rule

migrations/002_rls_policies.sql lets every signed-in user, including an anonymous guest, read every active scenario. The row includes insider knowledge, the blueprint, the briefing, and the role briefs. The browser does not call this table. A caller using the public key against the database API does. The app screens go through the server, covered in the next section.

Now 
CREATE POLICY "Anyone authenticated can view active scenarios"
  ON scenarios FOR SELECT
  USING (is_active = true AND auth.role() = 'authenticated');
After 
DROP POLICY IF EXISTS "Anyone authenticated can view active scenarios"
  ON public.scenarios;

CREATE POLICY "Creators and admins can view scenarios"
  ON public.scenarios
  FOR SELECT
  TO authenticated
  USING (
    created_by = auth.uid()
    OR EXISTS (
      SELECT 1 FROM public.user_profiles up
      WHERE up.id = auth.uid()
        AND up.role = 'admin'
    )

A direct read returns a row only to the creator or an admin. A guest, a player, and another trainer get nothing from the public key. Players still receive the scenario from GET /api/scenarios/:id, with insider knowledge and the blueprint removed.

New helpers in server/lib/access.ts

These sit next to the existing session helpers and use the same service-role client. Do not add an unused admin set. The route checks user.role === 'admin' directly.

export async function sessionTrainerScenarioIds(userId: string): Promise<string[]> {
  const { data } = await supabaseAdmin
    .from('sessions')
    .select('scenario_id')
    .eq('trainer_id', userId);
  return [...new Set((data ?? []).map((row) => row.scenario_id).filter(Boolean))] as string[];
}

export async function joinedScenarioIds(userId: string): Promise<string[]> {
  const { data } = await supabaseAdmin
    .from('session_participants')
    .select('session_id, sessions!inner(scenario_id)')
    .eq('user_id', userId);
  const ids = (data ?? []).map((row) => {
    const session = row.sessions as { scenario_id: string } | { scenario_id: string }[];
    const one = Array.isArray(session) ? session[0] : session;
    return one?.scenario_id;
  });
  return [...new Set(ids.filter((id): id is string => typeof id === 'string' && id.length > 0))];
}

export function redactScenarioForPlayer<T extends Record<string, unknown>>(row: T): T {
  const copy = { ...row };
  delete copy.insider_knowledge;
  delete copy.blueprint;
  return copy;
}
  • sessionTrainerScenarioIds is the set of scenarios this person is running. They still need the ground truth, even when someone else created the scenario.
  • joinedScenarioIds is the set of scenarios where this person is only a participant.
  • redactScenarioForPlayer removes the two trainer-only documents. Description, briefing, and initial_state stay, so the phone can still read the country.

05 · Database

Five functions

These functions are SECURITY DEFINER. They run with the owner's rights and ignore row security. Postgres grants execute to everyone by default, and the live database still lets the anon role call them. Nothing in server/ calls them. The server writes events, sentiment, and notifications with the service-role client.

  • log_session_event inserts an event for whatever session id it is given.
  • update_sentiment_snapshot inserts a sentiment row for whatever session id it is given.
  • get_unread_notification_count returns the unread count for whatever user id it is given.

Microphone

There is no role check and no session check. useVoiceInput posts the recording with the current token and no session id. The button is on chat, the decision form, the map, and the legacy War Room. A guest who has only signed in anonymously, and has never joined, can use it.

Today

Helper

export async function canTranscribe(user: AccessUser): Promise<boolean> {
  if (user.role === 'trainer' || user.role === 'admin') return true;
  const { count } = await supabaseAdmin
    .from('session_participants')
    .select('user_id', { count: 'exact', head: true })
    .eq('user_id', user.id);
  return (count ?? 0) > 0;
}

09 · Server

Rate limit

server/index.ts imports jsonwebtoken only for this. The global limiter allows 10,000 requests per 15 minutes in production. The key is a user id taken from the bearer token with jwt.decode, which does not check the signature. A token that was never issued can still supply a sub, and each different value gets its own budget. The join limiter and the contact limiter already key by IP. They stay.

requireAuth later calls supabaseAdmin.auth.getUser(token), which does check the token. The limiter runs first, so it cannot see req.user.

Today

const decoded = jwt.decode(token) as { sub?: string } | null;
if (decoded?.sub) return `user:${decoded.sub}`;

Verify first, then count

Delete import jwt from 'jsonwebtoken'. Add this middleware immediately before app.use('/api/', limiter). It stores only a verified user id. It does not set req.user, so requireAuth still checks the token and still loads the profile.

interface RateLimitedRequest extends Request {
  rateLimitUserId?: string;
}

app.use('/api/', async (req, _res, next) => {
  const header = req.headers.authorization;
  if (!header?.startsWith('Bearer ')) return next();
  const token = header.slice('Bearer '.length).trim();
  if (!token) return next();
  try {
    const { data } = await supabaseAdmin.auth.getUser(token);
    if (data?.user?.id) (req as RateLimitedRequest).rateLimitUserId = data.user.id;
  } catch {
    // an unusable token falls through to the IP key
  }
  next();
});

keyGenerator: (req) => {
  const userId = (req as RateLimitedRequest).rateLimitUserId;
  if (userId) return `user:${userId}`;
  const ip = req.ip ?? req.socket.remoteAddress ?? 'unknown';
  if (ip === 'unknown') return 'unknown';
  return ipKeyGenerator(ip);
}

A real signed-in user still has their own 10,000-request budget. A missing or rejected token shares the IP budget. The health-check skip stays. This adds one auth lookup on each API request that sends a bearer token, and requireAuth still does a second lookup. That is the cost of not trusting an unverified token. Do not remove the lookup inside requireAuth as part of this change.
